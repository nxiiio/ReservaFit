# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ReservaFit is an academic MVP for booking slots at independent neighborhood gyms (Chile). UI copy is Spanish. It is a monorepo: a React Router SPA at the root and Spring Boot microservices behind a gateway in `ReservaFit-Backend/`.

## Commands

Frontend (root, **pnpm** — not npm):

- `pnpm dev` — Vite dev server on `http://localhost:5173` (the user usually already has one running; don't start a second one, it will grab 5174)
- `pnpm typecheck` — `react-router typegen && tsc`; the main correctness check
- `pnpm build` — also worth running after auth changes: it exercises the SPA-mode prerender, which can break if browser-only code leaks into the route tree

There is no linter and no frontend test suite.

Backend (Java 25, Maven wrapper):

- `docker compose up -d mysql rabbitmq` (repo root) — only the infrastructure: MySQL on `localhost:3306` and RabbitMQ on `localhost:5672` (panel on `http://localhost:15672`, `reservafit`/`reservafit`), needed by every service
- `cd ReservaFit-Backend`, then one terminal per service: `./mvnw -pl api-gateway spring-boot:run` (8080), `-pl ms-usuarios` (8081), `-pl ms-reservas` (8083), `-pl ms-gimnasios` (8082). Start ms-reservas before ms-gimnasios (see the RabbitMQ section).
- `./mvnw compile` / `./mvnw test` from `ReservaFit-Backend` builds every module; only `ms-reservas` has tests (single test: `./mvnw -pl ms-reservas test -Dtest=ClassName#method`)
- On Windows, stopping the Maven process does not always kill the forked JVM. If a port is busy: `netstat -ano | grep :8080`, then `taskkill //PID <pid> //F`.

Docker (repo root, see the Docker section):

- `docker compose up --build` — MySQL, RabbitMQ, the four backend services, and the SPA (nginx) on `http://localhost:5173` with the gateway on `http://localhost:8080`, configured from `.env` (template: `.env.example`). Don't run it next to `pnpm dev`: both want port 5173.

## Frontend architecture

- React Router v8 framework mode with `ssr: false` (SPA mode). Routes are declared in `app/routes.ts`: a `routes/layout.tsx` layout (shared footer) wrapping `/`, `/login` and a nested `routes/app-layout.tsx` layout for signed-in pages: `/reservas` (gym catalog), `/gimnasios/:id` (schedule and booking) and `/mis-reservas` (my bookings).
- Tailwind v4 via `@tailwindcss/vite`; design tokens live in `app/app.css`. The repo sits in OneDrive, which sometimes makes Tailwind miss newly created files. Re-saving `app/app.css` forces a rescan.

### Auth (MSAL, Microsoft personal accounts)

- `app/authConfig.ts` holds the MSAL config, reading `VITE_AZURE_CLIENT_ID`, `VITE_AZURE_REDIRECT_URI` and `VITE_API_SCOPE` from `.env` (typed in `app/vite-env.d.ts`). It throws at import time if any are missing. `.env` is gitignored and not readable by Claude; ask the user for variable names, not values.
- Authority is `https://login.microsoftonline.com/consumers`: the app registrations target personal Microsoft accounts.
- `app/entry.client.tsx` is a custom client entry. It creates and `initialize()`s the `PublicClientApplication` and wraps `<HydratedRouter/>` in `<MsalProvider>`. Keep MSAL here, out of `root.tsx`/route modules: it is the browser-only boundary.
- `loginRequest` asks for the API scope itself, not Graph, so consent and the API token come from login. Otherwise `acquireTokenSilent` falls back to a hidden iframe, which times out for personal accounts. `prompt: "select_account"` is set so users can switch accounts.
- Route guards: `routes/login.tsx` redirects to `/reservas` when authenticated, and `routes/app-layout.tsx` redirects to `/login` when not (or when the profile is incomplete), covering every signed-in page. Both wait for `inProgress === InteractionStatus.None` before deciding. The app layout also renders `AppNav` (NavLinks + logout menu), so pages under it render only their content.
- Logout (in `AppNav`) is local only: `instance.clearCache()`, followed by a hard `window.location.assign("/login")`. `clearCache()` emits no MSAL event, so `MsalProvider` state would otherwise stay stale. `logoutRedirect()` would also sign the user out of Microsoft everywhere.
- `app/lib/` splits API concerns: `api.ts` only holds the axios instance, the backend URL (the gateway: `VITE_API_BASE_URL`, default `http://localhost:8080`) and one function per endpoint; `auth-token.ts` has `acquireApiToken` (`acquireTokenSilent`, with redirect fallback on `InteractionRequiredAuthError` or `timed_out`); `api-errors.ts` parses backend error bodies (`getFieldErrors`, `getErrorMessage`, `getErrorStatus`). `app/lib/use-current-user.ts` calls `POST /api/usuarios/me` and returns the profile. API data types live in `app/types/` (`user.ts`, `gym.ts`, `booking.ts`), not in `api.ts`.
- User registration: the first `POST /api/usuarios/me` creates the user from token claims. A profile is "complete" when RUT, birth date and card data are all set, not when the user is new. Incomplete profiles see `CompleteProfileForm` on `/login`, and `/reservas` sends them back there. Complete profiles go straight to `/reservas`.
- `/reservas` shows the gym catalog (`components/reservas/`: `ReservasPanel`, `GymCard`). It loads `GET /api/gimnasios` once via `fetchGyms` (no token) and filters by comuna client-side. "Ver horarios" links to `/gimnasios/:id` (`GymBookingPanel`: date picker, availability grid, `POST /api/reservas`). `/mis-reservas` (`MyBookingsPanel`) lists bookings and cancels with an inline two-step confirm.
- Dates travel as `"YYYY-MM-DD"` strings; use `app/lib/dates.ts` (local-date parsing/formatting). Never `new Date("YYYY-MM-DD")` or `toISOString()`: both are UTC and shift the day in Chile.

## Backend architecture

- `ReservaFit-Backend/` is a Maven multi-module project. The parent `pom.xml` lists the modules and imports the BOMs. Each module is a separate Spring Boot app with its own `application.yaml`, under the package `cl.nxiiio.reservafit.<module>`:
  - `api-gateway` (8080): Spring Cloud Gateway Server WebMVC. Routes live in its `application.yaml`: `/api/usuarios/**` → ms-usuarios, `/api/gimnasios/*/disponibilidad` → ms-reservas (`order: -1`, so it wins over the next one), `/api/gimnasios/**` → ms-gimnasios, `/api/reservas/**` → ms-reservas. It does not validate tokens; it forwards the `Authorization` header unchanged.
  - `ms-usuarios` (8081), `ms-gimnasios` (8082), `ms-reservas` (8083): each has its own controllers, services, entities, DTOs, exceptions and `ApiExceptionHandler`, all split out of the original monolith.
- Versions: Spring Boot **4.0.8**. Do not bump to 4.1.x without checking Spring Cloud Azure support. `spring-cloud-azure-starter-active-directory` has no version in the module poms: it comes from the `spring-cloud-azure-dependencies` BOM (7.4.0) imported in the parent pom. Don't pin the starter directly. The gateway comes from the Spring Cloud BOM (`spring-cloud.version`, 2025.1.3, built against Boot 4.0.8); bump it in step with Boot.
- Auth: `config/SecurityConfig.java` and the `spring.cloud.azure.active-directory` block are copied unchanged into each of the three services; keep the three copies identical. Every request needs a JWT except `GET /api/gimnasios` and `/api/gimnasios/**` (the gym catalog and availability are public). The Azure starter auto-configures JWT validation (issuer, audience) from `spring.cloud.azure.active-directory.*`.
- CORS: the browser only talks to the gateway, and Spring MVC answers preflight `OPTIONS` requests itself instead of forwarding them, so the gateway answers CORS (`api-gateway/.../config/CorsConfig.java`). The gateway and each service's `SecurityConfig` allow the origins in `app.cors.allowed-origins` (env `CORS_ALLOWED_ORIGINS`, comma-separated, default `http://localhost:5173`). Each route has a `RemoveRequestHeader=Origin` filter so the services' own CORS config does not add duplicate `Access-Control-Allow-Origin` headers. Add that filter to any new route.
- `profile.tenant-id` must be the consumers tenant GUID `9188040d-6c67-4c5b-b112-36a304b66dad`. The starter rejects the `consumers` alias for resource servers. Tokens from the org tenant `569ca4b8-...` (such as client-credentials tokens) are correctly rejected with 401. Each service's `application.yaml` takes the tenant and the API client ID from `AZURE_API_TENANT_ID` / `AZURE_API_CLIENT_ID` (the audience, `app-id-uri`, is `api://` plus the client ID), defaulting to the committed values. They are not named `AZURE_TENANT_ID` / `AZURE_CLIENT_ID` on purpose: the Azure SDKs (`DefaultAzureCredential`) read those, so a shell-level value set for other Azure work would silently override ours in compose.
- Database: one shared MySQL (`reservafit_db`, the `mysql` service of the root `compose.yaml`), but each service only reads and writes its own tables: ms-usuarios `usuario`; ms-gimnasios `gimnasio`, `horario`; ms-reservas `reserva`, `usuario_replica`, `horario_replica`. Never read another service's table or add a JPA relation or foreign key across services; use ids. `ddl-auto: update` in each service creates only that service's tables. Data survives restarts (`docker compose down -v` wipes it). Credentials default to `reservafit`/`reservafit` and can be overridden with `DB_HOST`, `DB_USERNAME` and `DB_PASSWORD`.
- JPA entities use Lombok. Entity fields, table names and endpoint paths are Spanish (`/api/gimnasios`, `/api/usuarios`, `/api/reservas`); all other backend code (classes, methods, JSON fields) is English. No Java records: DTOs are Lombok classes (`@Getter @Setter @NoArgsConstructor @AllArgsConstructor`). Custom exceptions live in each service's `exception/` package (never in `service/`, which holds only services) and are mapped to status codes in that service's `ApiExceptionHandler`, which returns error bodies as field → message maps.
- ms-usuarios: `UserController` exposes `POST /api/usuarios/me` (201 when created, 200 when it already existed) and `PUT /api/usuarios/me/perfil` (400 on invalid data, 409 on a duplicate RUT; the RUT's format is validated, not its check digit). `UserService` keys users by the token's `oid` (`Usuario.microsoftOid`).
- ms-gimnasios: `GymController` exposes public `GET /api/gimnasios` (optional `?comuna=`, case-insensitive, sorted by name), `GET /api/gimnasios/{id}` and `GET /api/gimnasios/{id}/horarios` (both 404 when the gym is missing). `Gimnasio.imagenUrl` (JSON `imageUrl`) is a plain URL; seed images are hotlinked from Unsplash. Seed gyms and schedules live in its `data.sql`, which runs on every boot (`spring.sql.init.mode: always`, plus `defer-datasource-initialization: true` because Hibernate generates the schema). It uses fixed ids and `INSERT IGNORE`, so it never duplicates rows; keep it that way.
- ms-reservas: never calls the other services. It reads users and schedules from its local copies, `UsuarioReplica` (id = ms-usuarios' user id, plus `oid`, name and email) and `HorarioReplica` (id = ms-gimnasios' horario id, plus the gym's id, name, comuna and image for booking responses). RabbitMQ fills these copies (see the RabbitMQ section); if they are empty (RabbitMQ was down, or ms-gimnasios has not started yet), booking returns 404 and so does availability (a gym with no schedule copies is a 404). `Reserva` stores `usuarioId`, `gimnasioId` and `horarioId` as plain columns.
- Bookings: `BookingController` exposes `POST /api/reservas` (201; 400 past date, >30 days ahead or already-started slot today; 404 unknown horario or user; 409 slot taken), `GET /api/reservas/mias` (upcoming confirmed first, ascending; then past/canceled, descending) and `DELETE /api/reservas/{id}` (soft cancel, 200 with the booking; 404 also for another user's booking; 409 already canceled or slot already started). `AvailabilityController` exposes public `GET /api/gimnasios/{id}/disponibilidad?fecha=YYYY-MM-DD`, which returns each horario with `available`. A confirmed booking can be canceled until its slot starts (`BookingService.hasStarted`, which also drives the `cancellable` JSON field). `Reserva.fechaCreacion` uses `@CreationTimestamp`. `Reserva.activa` is TRUE while confirmed and NULL when canceled, and `uq_reserva_slot` is UNIQUE(gimnasio_id, horario_id, fecha, activa): NULLs are distinct (in MySQL and H2), so canceled rows never block re-booking. Never set `activa` to FALSE. "Today"/"now" come from the `Clock` bean (`config/ClockConfig`, America/Santiago); use `LocalDate.now(clock)` so tests can use a fixed clock.
- ms-reservas tests run on in-memory H2: `src/test/resources/config/application.yaml` overrides only the datasource, and `src/test/resources/data.sql` seeds `horario_replica` with gym 1's schedules. `config/CorsConfigTest` covers the configurable CORS origins of `SecurityConfig` (it assumes `CORS_ALLOWED_ORIGINS` is not set). Tests have no RabbitMQ: the same file sets `spring.rabbitmq.listener.simple.auto-startup: false`, so the "Broker not available" lines in the test output are expected.

## RabbitMQ

- Purpose: ms-usuarios and ms-gimnasios publish their data, and ms-reservas consumes it into `usuario_replica` and `horario_replica`. ms-usuarios and ms-gimnasios only produce; ms-reservas only consumes; the gateway does not use RabbitMQ.
- No shared code: each service has its own `messaging/` package with its own `RabbitNames` (the names it uses; never hardcode those strings elsewhere), its own copy of the message classes and its own `RabbitConfig`. The message classes `UserRegisteredEvent` and `SchedulePublishedEvent` (Lombok, full snapshots, never RUT or card data) exist both in the producer and in ms-reservas: the JSON field names are the contract, so a field or name change must be made on both sides. ms-reservas' converter has `setAlwaysConvertToInferredType(true)`, so a message is always read into the listener's parameter class even though the producer's class lives in another package.
- Topology, declared in ms-reservas' `messaging/RabbitConfig` (the producers' `RabbitConfig` only declares the exchange): topic exchange `reservafit.events`; queues `reservas.users` (binding `user.*`) and `reservas.schedules` (binding `schedule.*`), each with `x-dead-letter-exchange = reservafit.dlx` and `x-dead-letter-routing-key` = its DLQ name; direct exchange `reservafit.dlx` with exact bindings to `reservas.users.dlq` and `reservas.schedules.dlq`. Messages are JSON (`JacksonJsonMessageConverter`). Because the queues are created by ms-reservas, ms-gimnasios must start after it: otherwise its schedules find no queue and come back as `log.warn` (restart ms-gimnasios to republish). `compose.yaml` enforces that order; with `./mvnw`, start ms-reservas first. Changing an existing queue's arguments makes RabbitMQ refuse the redeclaration (`PRECONDITION_FAILED`): delete the queue in the panel or `docker compose down -v` first.
- `user.registered`: `UserService.getOrCreate` calls `messaging/UserEventPublisher` on every login, not only the first, so a copy that missed a message is fixed on the next login. A publish failure (`AmqpException`) is logged and does not break the login.
- `schedule.published`: `messaging/SchedulePublisher` in ms-gimnasios publishes every schedule (with its gym, via `ScheduleRepository.findAllWithGym`) on `ApplicationReadyEvent`, since schedules only come from `data.sql`. Restarting ms-gimnasios republishes them.
- ms-reservas: `messaging/UserReplicaListener` and `ScheduleReplicaListener` save the copy with the original id, so `save()` inserts or replaces and duplicate messages are harmless.
- Failures: the consumer retries 4 times in total (`spring.rabbitmq.listener.simple.retry`, waits of 1s, 2s and 4s), then `messaging/DeadLetterRecoverer` (ms-reservas, picked up by Spring Boot as the only `MessageRecoverer`) logs the message with `log.error` and rejects it without requeue, so RabbitMQ moves it to the DLQ, where it stays (nothing consumes the DLQs; inspect or re-send them from the panel). On the producer side (`publisher-returns`, `template.mandatory`, `publisher-confirm-type: correlated`), the producers' `RabbitConfig` logs messages no queue accepted (`log.warn`) and publishes RabbitMQ did not confirm (`log.error`).
- Logs go to the console and to `logs/<service>.log` (relative to the working directory; `/app/logs` in Docker). Connection settings: `RABBITMQ_HOST`, `RABBITMQ_USERNAME`, `RABBITMQ_PASSWORD`, defaulting to `localhost` and `reservafit`/`reservafit`.

## Docker

- Frontend image (`Dockerfile`, root): `node:22-alpine` builds with pnpm, `nginx:stable-alpine` serves `build/client` using `docker/nginx.conf` (SPA fallback to `index.html`, a real 404 for a missing `/assets/` file, 1-year cache for `/assets/`, `GET /healthz` for the healthcheck). `.dockerignore` keeps `.env*`, `docs/`, `*.md` and the backend out of the build context.
- Backend image (`ReservaFit-Backend/Dockerfile`): one Dockerfile for every module, chosen with the `MODULE` build arg (`api-gateway`, `ms-usuarios`, `ms-gimnasios`, `ms-reservas`). `maven:3.9-eclipse-temurin-25` runs `mvn -pl $MODULE -am package -DskipTests` (it copies every module's `pom.xml` first, so a new module must be added there too), `eclipse-temurin:25-jre` runs the jar as a non-root user with `exec java $JAVA_OPTS -jar`. It does not use `mvnw` (its git file mode is 644, so it would not be executable in the image). The JRE image ships without curl, so the runtime stage installs it for the healthchecks, which live in `compose.yaml` because each service has a different port and endpoint.
- `compose.yaml` builds the frontend and one backend image per module, and reads `.env` from the repo root. Only `mysql` (3306), `rabbitmq` (5672 and the panel on 15672), `api-gateway` (`BACKEND_PORT`, 8080) and `frontend` are published; the gateway reaches the services by name through `USUARIOS_URL`, `GIMNASIOS_URL` and `RESERVAS_URL`, and the services reach MySQL and RabbitMQ through `DB_HOST=mysql` and `RABBITMQ_HOST=rabbitmq`. Start order: mysql and rabbitmq → ms-usuarios and ms-reservas → ms-gimnasios (it publishes into queues that ms-reservas creates) → gateway → frontend, each waiting for the previous to be healthy. The frontend is published as `5173:80` on purpose: `http://localhost:5173` is the only SPA redirect URI registered in Azure.
- `VITE_*` values are build args because Vite inlines them into the bundle: changing them needs `docker compose up --build`. Backend variables (`AZURE_API_*`, `CORS_ALLOWED_ORIGINS`) are read at startup. Nothing is required at the compose level, so `docker compose up -d mysql` works without a `.env`; the frontend Dockerfile fails the build when `VITE_AZURE_CLIENT_ID` or `VITE_API_SCOPE` is empty, and `AZURE_API_CLIENT_ID` defaults to the committed API client ID. Changing `FRONTEND_PORT` or `BACKEND_PORT` moves the derived defaults of `VITE_AZURE_REDIRECT_URI`, `VITE_API_BASE_URL` and `CORS_ALLOWED_ORIGINS`, but a new frontend port must also be registered as a redirect URI in Azure.
- MySQL data lives in the `mysql-data` volume and RabbitMQ's (queued messages, DLQs) in `rabbitmq-data`, so both survive `docker compose down`; `docker compose down -v` wipes them.
